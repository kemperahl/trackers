Migration Plan

Step-by-step network cutover (Nest → UniFi) and Home Assistant migration (Mac Mini/UTM → dedicated Mini PC), run as two separately-validated changes rather than one combined leap. Mirrors the Obsidian Migration Runbook doc — update both together.

Phase 0 — Prep

  • Confirm exact Nest WiFi router model (determines clean bridge/AP mode vs. double-NAT later)
  • Note anything worth preserving: static IP reservations, port forwards, current SSID/password
  • HA: full backup (Settings → System → Backups), download a copy off-device
  • Ring app credentials/2FA on hand
  • Rack-mount and power UCG-Max + Flex switch, let firmware update

Phase 1 — Sandbox the new network behind the old one

Zero blast radius — nothing in the house depends on this yet.

  1. Cable: Nest LAN port → UCG-Max WAN port
  2. Adopt UCG-Max, update firmware, run setup (gets a temporary private IP from Nest)
  3. Cable UCG-Max → Flex switch via SFP+ DAC, adopt switch
  4. Build VLANs: Trusted, IoT, Lab, Guest
  5. Base firewall rules: IoT→Internet allow / IoT→Trusted block, Lab→Internet allow / Lab→Trusted block, Trusted→Lab allow, Guest isolated except internet
  6. Create SSIDs: Trusted, IoT, Guest — IoT SSID is a new addition (Ring + B-hyve are WiFi-only, need a home on the IoT VLAN; Hue + SmartThings stay wired)
  7. Test each SSID with a throwaway device before connecting anything real

Configuring Trusted → HA (the one deliberate exception)

  1. Fixed IP first: DHCP reservation for the HA Mini PC
  2. Separate zones: don't leave Trusted + IoT in the same default "Internal" zone
  3. Default Trusted→IoT = Block (HA is the exception, not the rule)
  4. Add exception: Source = Trusted, Destination = HA's reserved IP, Ports 8123 (+443), Allow — evaluated before the general block
  5. Test: HA loads from a Trusted device; another IoT device (e.g. Hue bridge UI) does not

One-directional only — HA cannot reach back into Trusted (IoT→Trusted block applies to it too). A future need for HA to reach into Trusted needs its own narrow exception, not a blanket opening — see HA → Sonos below for a concrete example.

Configuring HA → Sonos (the mirror-image exception)

Sonos lives on Trusted, not IoT — both the native Sonos app and AirPlay depend on mDNS/Bonjour multicast, which doesn't cross VLANs without a fragile reflector setup, so Sonos sits with the phones/Macs that control it instead.

  1. Static IPs / DHCP reservations for the Sonos speakers on Trusted
  2. Firewall rule: Source = HA's reserved IP, Destination = Sonos IPs, Allow — scoped to the ports Sonos control uses, not a blanket IoT→Trusted opening
  3. Configure HA's Sonos integration with the static IPs directly rather than relying on auto-discovery — sidesteps needing multicast to cross the boundary
  4. Test: HA casts to a speaker successfully; everything else on IoT still can't reach Trusted

Known limitation, not solved here: Guest→Trusted stays blocked, so guests can't AirPlay to Sonos from their own phones on Guest WiFi.

Bambu P1S 3D printer — stays on IoT, unlike Sonos

Controlled from the Mac Mini and phone (both Trusted) too, but stays on IoT — not on LAN-only mode, so it phones home to Bambu's cloud, a real reason to keep it segmented. Bambu Studio's auto-discovery is broadcast (SSDP), which can't cross a routed VLAN boundary at all — no firewall rule fixes that. But unlike AirPlay, discovery only needs to work once: add the printer manually by IP + access code in Bambu Studio / Bambu Handy, then a narrow firewall exception handles ongoing control.

  1. Reserve a static IP for the printer on IoT
  2. Firewall rule: Source = Mac Mini + phone, Destination = printer's IP, Allow — scoped to ports 990 (FTPS, file transfer), 8883 (MQTTS, control/status), 6000 (camera stream); confirm against the printer's own network settings, firmware can shift these
  3. Add the printer manually by IP + access code in Bambu Studio and Bambu Handy, once

Not yet configured — printer is still on the old Nest network as of 2026-08-14. Do this as part of its migration, not before.

Phase 2 — Validate new HA hardware, still on the OLD network

  1. Flash HAOS onto the new Mini PC
  2. Restore the Phase 0 backup
  3. Shut down the Mac Mini's HA VM cleanly, move the Zigbee dongle to the new Mini PC (only exists once — forces this step to be sequential)
  4. Plug the new Mini PC into the old Nest network (same flat LAN) — testing hardware only, no VLAN yet
  5. Verify Zigbee, Hue, SmartThings, automations, dashboards all come back clean
  6. Run 24–48h, Mac Mini VM off but not deleted — instant rollback

Phase 3 — Cutover (~15–30 min outage)

  1. Unplug WAN handoff from Nest, plug into UCG-Max
  2. Confirm UCG-Max gets a public IP + internet
  3. Plug Nest's LAN port into the Flex switch; use real bridge/AP mode if available, else disable Nest's own DHCP

You likely don't have UniFi APs installed yet — Nest's own radios remain the only WiFi, just downstream of UCG-Max now. Keep Nest's SSID name/password exactly as-is through this phase; there's no separate "new" SSID to converge with until APs exist.

Phase 3.5 — Bring up UniFi APs (once purchased)

  1. Install/power APs, adopt, configure wireless mesh backhaul
  2. Create Trusted/IoT/Guest SSIDs on the APs — this is when "new" WiFi hardware actually starts broadcasting
  3. Use SSID names visibly distinct from Nest's during this window — matching names risks a client silently landing on Nest's isolated network if it isn't a clean bridge, with no way to tell which devices have migrated
  4. Migrate WiFi clients deliberately (Phase 4) rather than relying on auto-reconnect
  5. Only converge/simplify SSID names after Nest is fully decommissioned (Phase 6)

Phase 4 — Migrate devices, one at a time

  • Ring: app → device → Change Wi-Fi Network → new IoT SSID, one device at a time. Alarm base station: wire to the switch directly if it has Ethernet. Sensors/keypad (Z-Wave) unaffected.
  • Hue Bridge: Ethernet only — move the cable to IoT VLAN, app rediscovers automatically.
  • SmartThings: same as Hue — move cable, rediscovers (may need a manual reconnect tap).
  • B-hyve: WiFi-only — app → WiFi Setup → new IoT SSID.
  • Bambu P1S printer: WiFi onto new IoT SSID, then reserve its static IP, add the Mac Mini/phone → printer exception (ports 990/8883/6000), re-add the printer manually by IP in Bambu Studio/Handy.
  • Synology: move cable to Trusted VLAN, confirm DSM reachable, re-check Mac Mini backup target resolves.
  • Mac Mini / phones / laptops: join new Trusted SSID at your convenience.
  • Guests: point to new Guest SSID once live.

Phase 5 — Move HA into its final home

  1. Physically move the validated Mini PC into the rack, onto its patch-panel drop
  2. Assign that port to the IoT VLAN
  3. Confirm the DHCP reservation still applies
  4. Confirm HA's UI loads from a Trusted device
  5. Spot-check integrations now that Hue/SmartThings/Ring/B-hyve have also moved to IoT VLAN
  6. Stable a few days → decommission the Mac Mini's HA VM (keep the final backup archived on the Synology)

Phase 6 — Decommission Nest

  1. Confirm Nest/Google Home app shows no connected devices left
  2. Power down Nest router + points — keep as a labeled spare for a few weeks
  3. Update Shopping List / Parts List to drop Nest as active infrastructure
  4. Safe to simplify/rename SSIDs now — no second network left to collide with

Verification checklist

Run after Phase 3, and again after Phase 5.

  • Internet reachable from Trusted, IoT, and Lab VLANs
  • IoT → Trusted blocked; Lab → Trusted blocked
  • Trusted → HA reachable; Trusted → Lab reachable (Grafana/Portainer)
  • Guest isolated except internet
  • All Ring devices online; Hue scenes fire; SmartThings devices online; B-hyve schedule runs
  • No "unavailable" entities in HA, automations firing
  • Synology backups completing on the new network
